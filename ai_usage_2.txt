5. NAME LOOKUP INSIDE MEMBER FUNCTIONS
==================================================

ChatGPT helped me define a precise name lookup rule for member functions.

The rule used in the project is:

1. local variables and parameters;
2. fields of the current structure;
3. global variables.

This was important because a parameter, structure field and global variable can have the same name.

I also used the rule that other member functions of the same structure can be called by name from inside a member function.

I understood that the semantic analyzer must resolve what every identifier refers to before LLVM generation.

6. INTEGER TYPES, WIDENING AND OVERFLOW
==================================================

Prompts included:

"чекай а що ми будемо робити з оверфлоу? та з визначенням типу числа"

"давай виправимо це все перед llvm"

This part was significantly discussed with ChatGPT.

The rules implemented were:

- integer literals receive the narrowest type they fit;
- values fitting in signed 32 bits use `i32`;
- larger values fitting in signed 64 bits use `i64`;
- literals outside signed `i64` are compilation errors;
- implicit `i32 -> i64` widening is allowed;
- implicit `i64 -> i32` narrowing is not allowed;
- arithmetic returns the wider integer type;
- integer comparisons may compare `i32` and `i64`;
- booleans cannot participate in integer arithmetic.

What I used:
- helper logic for determining the type of an integer literal;
- an `is_assignable` rule;
- expression type information stored by the semantic pass;
- widening before LLVM operations when needed.

I also handled the edge values:

- `-2147483648`;
- `-9223372036854775808`.

I understood the difference between two kinds of overflow:

1. A literal outside the supported range can be detected during semantic analysis.
2. Arithmetic such as `2000000000 + 2000000000` depends on runtime values and therefore needs a runtime overflow check in the generated LLVM code.

8. LLVM FUNCTIONS
==================================================

Prompt:

"давай далі до llvm functions"

ChatGPT suggested generating functions in two phases:

1. declare all LLVM functions;
2. generate all function bodies.

I used this because MeowLang supports:

- recursion;
- calls to functions declared later.

User-defined LLVM function names use a prefix so that MeowLang functions do not collide with names such as `main`, `printf` or `scanf`.

Function parameters are stored in local LLVM stack slots so that they can be handled using the same variable logic as local variables.

For `mi`, the generated LLVM code returns the expression value, applying `i32 -> i64` widening where required.

Function calls evaluate their arguments and widen them according to the parameter types determined by semantic analysis.

What I understood:
- LLVM needs the callee declaration before a call can reference it;
- declaring every function first solves both recursion and forward-call resolution;
- LLVM builder calls must not be used as the semantic type checker.

9. LLVM STRUCTURES
==================================================

Prompt:

"ок давай до llvm structs"

ChatGPT suggested representing every MeowLang structure as an LLVM identified structure type.

The implementation uses two passes:

1. create all named LLVM structure types;
2. fill their bodies with their field types.

This allows one structure type to refer to another structure declared later.

Fields are accessed using LLVM `getelementptr` (GEP).

The field index comes from the semantic structure metadata.

What I used:
- identified LLVM structure types;
- field indices from semantic analysis;
- a helper that produces the address of a variable or field;
- recursive field-address generation for chains such as `c.center.x`;
- temporary storage for constructed objects.

What I understood:
- LLVM does not know source-level field names;
- it accesses structure fields by numeric index;
- therefore the semantic symbol table must preserve each field's declaration order and index.

10. LLVM MEMBER FUNCTIONS
==================================================

Prompt:

"ок давай далі"

ChatGPT explained that a member function can be lowered to a normal LLVM function whose first hidden parameter is a pointer to the object.

For example, conceptually:

`Point.getX()`

becomes an LLVM function similar to:

`Point_getX(self_pointer)`

I used:

- one LLVM function for each structure/member-function pair;
- a hidden object pointer as the first parameter;
- field access through this object pointer;
- the same normal parameters after the hidden object pointer.

For bare field names inside a member function, the code generator can use the current object pointer after semantic lookup has established that the identifier refers to a field.

For bare member calls inside another member function, the current object pointer is passed automatically.

What I understood:
- member functions do not need a completely different LLVM function model;
- they can be represented as ordinary functions with an explicit hidden object pointer;
- semantic analysis is responsible for checking mutability before code generation.

11. INPUT AND OUTPUT
==================================================

Prompt:

"окей давай до o/i  іпоясни як це працює"

ChatGPT explained how MeowLang I/O can use the C runtime.

The implementation uses declarations for:

- `scanf`;
- `printf`.

`📚()`:

1. allocates an `i32` slot;
2. calls `scanf("%d", pointer)`;
3. loads and returns the value.

`🐾(...)` uses:

- `%d` for `i32`;
- `%lld` for `i64`;
- textual `true` or `false` for bool;
- `%s` for string literals.

The project defines print as adding one newline after the complete printed value.

For structures, printing is generic:

- print the structure name;
- iterate through its semantic field metadata;
- use GEP to reach each field;
- load and print the value;
- recursively print nested structure fields.

Example format:

`Point{x: 10, y: 20}`

What I understood:
- LLVM itself does not provide high-level terminal I/O;
- the generated module declares external C functions and `clang` links them with the system C library;
- generic object printing is possible because the compiler already has complete structure field metadata.

15. MY UNDERSTANDING
==================================================

The compiler now has a clear sequence of phases.

The lexer converts UTF-8 source text into tokens and tracks source positions.

The recursive-descent parser converts the token stream into an AST.

The semantic analyzer walks the AST before any LLVM IR is generated. It resolves declarations, manages scopes, determines expression types, checks mutability, validates function calls, validates structures and fields, and rejects invalid programs.

The semantic analyzer also determines when the only supported implicit conversion, `i32 -> i64`, is valid.

The LLVM generator assumes that semantic analysis has already accepted the program. It therefore focuses on generating IR instead of discovering source-language type errors.

Functions are declared before their bodies so recursion and forward calls work.

Structures become LLVM structure types. Fields are accessed by their numeric indices using GEP.

Member functions are implemented as LLVM functions with a hidden pointer to the receiver object.

Input and output use C library functions declared in LLVM and linked by Clang.

Compile-time literal overflow and runtime arithmetic overflow are different problems: literal range errors are rejected by semantic analysis, while runtime arithmetic is protected by generated overflow checks.

Testing the complete source-to-executable pipeline is important because valid AST and semantic behavior do not guarantee that the generated LLVM module actually builds or produces the expected output.
